## 무엇을 만드나

3D 배치도에서 방을 고르면 그 방을 예약 신청할 수 있게 한다. 담당 교사가 승인해야
확정된다.

정해진 것:

| 항목 | 결정 |
|---|---|
| 저장소 | 구글 앱스크립트 + 스프레드시트 |
| 권한 | **나누지 않는다.** 누구에게나 `예약하기` 버튼 |
| 시간 단위 | 교시별 / 시간별 **둘 다** |
| 확정 | 담당 교사가 확인하고 **승인해야** 확정 |

아직 안 정한 것은 맨 아래 [남은 결정](#남은-결정) 에 모아 뒀다.

## 1. 구조 — 관리 화면을 따로 만들지 않는다

```
GitHub Pages (지금 이 사이트, 정적)
        │  fetch
        ▼
  Apps Script 웹앱          ← 신청 접수 · 현황 조회
        │
        ▼
   구글 스프레드시트  =  예약 장부
        ▲
        │  담당 교사가 직접 연다
        └─ 상태 칸을 대기 → 승인 으로 바꾸면 그게 곧 승인
```

**이 스택을 고른 가장 큰 이유가 이것이다.** 교사가 시트에서 `상태` 칸만 바꾸면
승인이 끝난다. 관리자 로그인, 관리자 화면, 권한 시스템을 **하나도 만들지 않아도 된다.**
프론트엔드는 읽기만 하므로 승인 기능 때문에 화면을 고칠 일이 없다.

서버 관리도 없고 학교 구글 계정으로 무료다.

### 사람이 시트를 손으로 고치기 때문에 생기는 문제

셋 다 대비가 필요하다.

- **오타** — `상태` 열에 데이터 확인(드롭다운)을 걸어 `대기 / 승인 / 반려 / 취소`
  네 개만 고르게 한다. 프론트가 모르는 값이 들어가면 그 예약은 화면에서 사라진다.
- **동시 편집** — 교사가 시트를 열어둔 동안에도 신청은 들어온다. 앱스크립트 쓰기는
  `LockService` 로 직렬화한다.
- **행 삭제** — 취소도 상태값으로 표시하고 **행은 절대 지우지 않는다.** 지우면
  예약번호가 겹친다(번호를 마지막 행 번호로 만든다). 이미 알려준 번호와 같아지면
  취소가 엉뚱한 예약을 건드린다.
- **공유 범위** — 담당 교사만 편집자로 둔다. 웹앱을 *"나(소유자) 권한으로 실행"* 으로
  배포하면 학생 계정에 시트 권한을 하나도 주지 않고도 신청이 기록된다.

### 앱스크립트의 한계 (미리 알고 있을 것)

- 실행 시간·호출 횟수에 하루 한도가 있다. 학교 규모에서는 문제되지 않지만,
  지도 화면이 방을 옮길 때마다 조회하면 금방 늘어난다 → **읽기 응답은 `CacheService`
  로 몇 분 묶는다.**
- 응답이 빠르지 않다(수백 ms~1초). 버튼을 누른 뒤 기다리는 표시가 필요하다.
- 스프레드시트가 수천 행이 되면 느려진다. 학년도가 끝나면 시트를 갈아 끼운다.

## 2. 방을 무엇으로 가리킬 것인가

**이 문서에서 제일 중요한 항목이다.**

지금 `rooms.json` 의 방 `id` 는 `동-층F-이름` 이다 (`3동-3F-하늬콜로키움`).
**이걸 예약 키로 쓰면 안 된다.** 도면을 고치면 곧바로 깨진다. 실제로 2026-07-28
하루 작업에서 이런 일이 있었다.

- `2동 홀` → `2동 1층 홀` 로 이름을 바꿈 → id 변경
- 4동을 새로 나누면서 **26개 방의 소속이 2동 → 4동** → id 26개가 한꺼번에 변경

예약 시스템이 이미 돌고 있었다면 그날 하루에 26개 방의 예약이 전부 고아가 됐다.

반면 Sweet Home 3D 가 방마다 붙이는 UUID(`room-de679dc7-…`)는 이름을 바꾸든 동
분류가 바뀌든 그대로다. 확인해 보니 **7/28 초기 도면의 방 115개 중 108개(94%)가
지금도 같은 UUID** 였다. 그 사이 이름이 바뀌고 폴리곤이 합쳐졌는데도 그렇다.

### 그래서

1. **파서가 UUID 를 `sourceId` 로 같이 내보낸다.** ✅ **이미 넣어 뒀다** —
   예약을 만든 뒤에 넣으면 그 사이 쌓인 데이터를 옮겨야 해서 미리 해뒀다.
   `rooms.json` 의 방 178개 전부에 있고 값이 서로 겹치지 않는다.
   id 가 없는 방이 생기면 파서가 경고한다.

   ```jsonc
   { "id": "3동-3F-하늬콜로키움",                  // 사람이 읽는 용도. 바뀔 수 있다
     "sourceId": "room-7e62a8d6-b14c-4fb9-…",   // 예약이 붙잡을 키
     "name": "하늬콜로키움", "building": "3동", "floor": 3, … }
   ```
2. 예약은 `sourceId` 를 키로 쓴다.
3. 방을 **다시 그리면** UUID 도 바뀐다(위의 나머지 6%). 그래서 예약 행에
   `방이름`·`층`·`동` 을 **신청 시점 그대로 같이 저장**한다. UUID 가 사라져도
   사람이 어느 방인지 알아볼 수 있어야 한다.
4. 프론트는 `sourceId` 로 방을 못 찾으면 그 예약을 "이름으로만 남은 예약" 으로
   구분해 보여주고, 교사에게 정리를 알린다.

## 3. 시간 모델 — 저장은 시각으로, 표시는 교시로

교시별과 시간별을 둘 다 받을 때 흔한 실수가 **교시는 교시대로, 시각은 시각대로
저장**하는 것이다. 그러면 `5교시` 예약과 `14:00~15:00` 예약이 겹치는지 판단할 수 없다.

무엇으로 신청하든 **절대 시각으로 정규화해서 저장**하고, 교시로 신청한 경우에만
`교시` 라벨을 함께 남긴다.

```
신청: 5·6교시          ─(시간표 참조)─▶   저장: 13:20 ~ 15:10 , 교시 = "5,6"
신청: 14:00 ~ 14:30                 ─▶   저장: 14:00 ~ 14:30 , 교시 = (빈칸)

겹침 판정:  (시작A < 끝B) && (시작B < 끝A)      ← 규칙 하나로 끝
```

교시 라벨은 화면에 "5교시" 로 예쁘게 보여주는 용도이지 판정에는 쓰지 않는다.

위 두 줄이 실제로 겹치는지 화면에서 확인했다. 5·6교시로 잡아둔 예약이 있는 상태에서
`14:00~14:30` 을 시간별로 신청하려 하면 **"이미 예약됨" 이 뜬다.** 저장을 시각으로
통일했기 때문에 신청 방식이 서로 달라도 한 규칙으로 걸린다.

### 시간표

| 교시 | 시각 | |
|---|---|---|
| 1교시 | 08:20 ~ 09:10 | |
| 2교시 | 09:20 ~ 10:10 | |
| 3교시 | 10:20 ~ 11:10 | |
| 4교시 | 11:20 ~ 12:10 | |
| 점심 | 12:10 ~ 13:20 | 70분 |
| 5교시 | 13:20 ~ 14:10 | |
| 6교시 | 14:20 ~ 15:10 | |
| 종례 | 15:10 ~ 15:30 | 20분 — **예약 대상에서 뺀다** |
| 7교시 | 15:30 ~ 16:20 | 일반 학급은 여기까지 |
| 8교시 | 16:30 ~ 17:20 | 방과후 |
| 9교시 | 17:30 ~ 18:20 | 방과후 |

학기마다 바뀌므로 코드에 박지 않고 `src/config.js` 의 `PERIODS` 로 뺐다. 파서는
시간표를 쓰지 않으므로(도면과 무관하다) `plan.config.json` 이 아니라 프론트 설정이다.

```jsonc
"periods": [
  { "key": "1",     "label": "1교시", "start": "08:20", "end": "09:10" },
  { "key": "2",     "label": "2교시", "start": "09:20", "end": "10:10" },
  { "key": "3",     "label": "3교시", "start": "10:20", "end": "11:10" },
  { "key": "4",     "label": "4교시", "start": "11:20", "end": "12:10" },
  { "key": "lunch", "label": "점심",  "start": "12:10", "end": "13:20" },
  { "key": "5",     "label": "5교시", "start": "13:20", "end": "14:10" },
  { "key": "6",     "label": "6교시", "start": "14:20", "end": "15:10" },
  { "key": "hr",    "label": "종례",  "start": "15:10", "end": "15:30", "bookable": false },
  { "key": "7",     "label": "7교시", "start": "15:30", "end": "16:20" },
  { "key": "8",     "label": "8교시", "start": "16:30", "end": "17:20", "after": true },
  { "key": "9",     "label": "9교시", "start": "17:30", "end": "18:20", "after": true }
]
```

세 가지를 짚어둔다.

- **종례(20분)는 `bookable: false`.** 너무 짧아서 예약 단위로 의미가 없다.
  **점심(70분)은 연다** — 동아리 모임처럼 실제로 쓰는 시간대다. 아니면 이 값만 뒤집으면 된다.
- **8·9교시는 방과후**라 일반 학급 시간표에는 없다. 목록에는 두되 `after` 로 구분해
  화면에서 흐리게 보여주거나 접어둔다.
- **교시 사이에 10분씩 빈다.** 3·4교시를 이어서 신청하면 `10:20~12:10` 한 구간으로
  묶어 저장한다(중간 쉬는 시간 포함). 두 구간으로 쪼개 저장하면 겹침 판정만 복잡해진다.

### 교시 선택은 반드시 이어져 있어야 한다

한 구간으로 저장하는 이상 **떨어진 교시를 고를 수 없다.** 처음에는 아무 교시나
켰다 껐다 하게 뒀는데, 3교시와 5교시를 고르는 순간 구간이 `10:20~14:10` 이 되어
고르지도 않은 4교시가 딸려 들어갔다. 4교시가 이미 예약돼 있으면 화면에
**"고르지도 않은 시간이 이미 예약됨"** 이 떠서 무슨 일인지 알 길이 없다.

그래서 사이를 실제로 채워서 보여준다. 1교시를 켠 채 3교시를 누르면 2교시도 같이
켜진다 — 어차피 그 시간을 잡는 것이니 눈에 보이는 게 맞다. 사이에 **예약된** 교시가
있어 채울 수 없으면 누른 교시 하나로 새로 시작한다.

**'혼자 고를 수 있나' 와 '지나갈 수 있나' 는 다른 질문이다.** 종례는 20분뿐이라
단독으로는 못 고르게 해뒀지만, 6교시와 7교시를 이어 잡을 때는 지나갈 수 있어야 한다.
그 사이 20분도 당연히 같이 쓰는 것이기 때문이다. 막는 것은 이미 예약된 교시뿐이다.

### 불러오는 동안은 잠근다

앱스크립트 응답이 1~3초 걸린다. 그동안 교시를 고를 수 있게 두면 이미 예약된 교시를
고르고 신청 버튼까지 눌렀다가 서버가 거절한 뒤에야 알게 된다. 현황을 받아오는 동안
교시 칸을 흐리게 하고 클릭을 막는다.

요일마다 시간표가 다르면 `periods` 를 요일별로 나눈다. 지금은 매일 같다고 본다.

### ⚠ 이름으로 고르면 안 되는 이유 (실제로 겪은 일)

한때 `432` 로 이름을 훑으면 **두 방이 걸렸다.**

```
432                 ← 진짜 이 방
연극실 (431, 432)     ← 이름 안에 432 가 들어 있을 뿐
```

지금은 도면에서 `연극실 (431)` 로 고쳐 충돌이 없어졌지만, 이런 일은 또 생긴다.
**목록은 `sourceId` 로 못 박는다.** 실제로 그 뒤에 `432` 와 `433` 의 이름을 서로
맞바꿨는데도 UUID 는 그대로여서 설정을 한 글자도 고칠 필요가 없었다.

### 설정 (이미 들어가 있다)

`tools/plan.config.json` 의 `reservable` 이 목록이고, 파서가 해당 방에
`reservable: true` 를 붙인다. 이미 있는 `shaftWords`·`typeColors`·`typeHeights` 와
같은 패턴이다. 정원·비고(예: "사용 후 정리 필수")도 여기서 같이 주면 된다.

**방을 더 열거나 빼려면 이 설정만 고치고 파서를 다시 돌린다.** 뷰어 코드는 안 건드린다.

```jsonc
"reservable": {
  "room-b74df5b6-888a-420f-86a9-5b9b793eaff5": { "name": "제1과학실" },
  "room-a968ff58-9314-4344-bf48-5770381e33a9": { "name": "제2과학실" },
  "room-60cacae3-c08b-46cb-9d91-3e2bdcf45e21": { "name": "무용실" },
  "room-52233777-61ad-4652-9862-f85dc9bb5ab3": { "name": "대강의실" },
  "room-081e3d5b-1c88-40e3-bc31-6b186109e1ee": { "name": "422" },
  "room-74b6075e-127b-4b0f-a87d-6d54848ddea9": { "name": "423" },
  "room-bae7a448-39c5-498c-8870-d343ed8f4805": { "name": "432" },
  "room-798e4e67-61b8-47a3-a0cf-021e49a0749b": { "name": "433" },
  "room-2099ac30-81fe-4b53-b023-73c8cb07028e": { "name": "434" },
  "room-b2fea448-3551-4c8d-8624-e40eba8314e7": { "name": "연극실 (431)" },
  "room-3be71820-4ada-4e31-a53e-ca6212557933": { "name": "비주얼아트실 (435)" },
  "room-7e62a8d6-b14c-4fb9-9cc0-25114beb6d63": { "name": "하늬콜로키움" },
  "room-bd0c1e5b-57f5-40af-9d22-dc1dc403be49": { "name": "큰들마 콜로키움" }
}
```

`name` 은 사람이 설정을 읽을 때 어느 방인지 알아보라고 적어두는 것이고, 판정은
`sourceId` 로만 한다. **둘이 어긋나면 파서가 경고한다** — 방을 다시 그려 UUID 가
바뀌었다는 뜻이고, 그러면 그 방이 예약 화면에서 조용히 사라지기 때문이다.

## 5. 시트 열 구성

| 열 | 예 | 비고 |
|---|---|---|
| 신청시각 | `2026-05-12 09:31` | 앱스크립트가 찍는다 |
| 예약번호 | `R-2605-0142` | 취소·문의용. 신청자에게 보여준다 |
| sourceId | `room-de679dc7-…` | **진짜 키** |
| 방이름 | `331호 학습실` | 신청 시점 스냅샷 |
| 층 / 동 | `3` / `3동` | 신청 시점 스냅샷 |
| 날짜 | `2026-05-12` | |
| 시작 / 끝 | `13:50` / `14:40` | 정규화된 시각 |
| 교시 | `5` | 시간으로 신청했으면 빈칸 |
| 신청자 | `김○○` | 로그인이 없으므로 자기 신고 |
| 소속 | `2-3` | 학급 또는 동아리 |
| 연락 | | 교사가 확인할 수단 |
| 사유 | `스터디` | |
| **상태** | `대기` | **교사가 고치는 칸** (드롭다운) |
| 처리메모 | `그날 대청소라 반려` | 반려 사유. 신청자에게 보여준다 |

## 6. 상태 흐름

```
[신청] ──▶ 대기 ──교사──▶ 승인 ──▶ 확정
             │             │
             └─교사─▶ 반려   └─교사─▶ 취소
```

- **승인된 예약만** 지도와 시간표에 "예약됨" 으로 보인다.
- **대기 중인 신청은 다른 사람의 신청을 막지 않는다.** 막으면 아무나 대기를 걸어
  방을 잠글 수 있다. 겹치는 신청이 여럿이면 교사가 하나만 승인하고 나머지를 반려한다.
- 앱스크립트가 **승인 시점에 겹침을 다시 검사**해서, 이미 승인된 것과 겹치면 교사에게
  경고한다. 사람이 시트에서 직접 바꾸는 방식이라 이 검사가 마지막 안전망이다.

## 7. API (앱스크립트 웹앱)

| 요청 | 하는 일 |
|---|---|
| `GET ?action=slots&room=<sourceId>&date=<날짜>` | 그 방 그 날의 승인된 예약 + 교시 시간표 |
| `GET ?action=day&date=<날짜>` | 그 날 전체 방의 승인 현황 (지도에 칠하기용) |
| `POST action=request` | 신청 → 예약번호 반환 |
| `POST action=cancel` | 예약번호 + 신청자명으로 본인 취소 (대기 상태일 때만) |

읽기 응답은 `CacheService` 로 몇 분 묶는다.

## 8. 프론트엔드에 붙는 곳

**이미 있는 것에 얹는다. 새 화면을 만들지 않는다.**

- **방 정보 패널** (`#panel`) — 예약 가능한 방이면 `예약하기` 버튼과
  `오늘 3건 예약됨` 요약 한 줄. `src/main.js` 의 `openPanel()` 이 붙일 자리다.
- **예약 대화상자** — 날짜 / 교시·시간 전환 / 시간 선택 / 신청자 정보.
  확인 화면에 **"승인 후 확정됩니다"** 를 분명히 적는다. 누르자마자 잡힌 줄 알면
  그 방에 그냥 가버린다.
- **지도 위 표시** *(1차 범위에서 제외)* — 날짜를 고르면 예약된 방을 다른 색으로.
  `applyFilters()` 옆에 얹으면 된다.

## 9. 로그인이 없다는 것의 대가

누구나 예약 버튼을 누를 수 있다는 건 **아무 이름이나 적을 수 있다**는 뜻이다.
승인제가 방패라 가짜 신청이 확정되지는 않지만, 대비는 필요하다.

| 위험 | 대비 |
|---|---|
| 장난 신청이 쌓여 교사가 피곤해짐 | 같은 방·같은 날 신청 수 제한, 앞으로 N주 이내만 신청 가능 |
| 남의 이름으로 신청 | 연락처 필수. 승인 전에 교사가 당사자 확인 |
| 남의 예약을 취소 | 예약번호 **+** 신청자명이 맞아야, 그리고 대기 상태일 때만 |

---

## 10. 알림 — 없으면 시스템이 안 돈다

시트만으로는 교사가 신청이 들어온 걸 **모른다.** 승인이 안 되면 예약도 안 되므로
알림은 있으면 좋은 게 아니라 **필수다.**

- 신청이 기록된 직후 앱스크립트가 담당 교사에게 메일을 보낸다, 또는
- 하루 한 번 대기 건수를 요약해 보내는 트리거를 건다 (메일이 너무 잦으면 이쪽)

승인·반려 결과도 신청자에게 알려야 한다. 연락처를 메일로 받으면 같은 방법을 쓴다.

### 답이 없으면 이 값으로 만든다

만들기 전에 한 번 확인하고, 다르면 그때 바꾼다. 전부 설정으로 뺄 것이라
나중에 고치는 비용은 작다.

| | 기본값 | 다르게 하면 |
|---|---|---|
| **담당 교사** | 한 명. 시트 공유 계정 하나 + 알림 메일 하나 | 방마다 다르면 시트에 담당자 열이 붙고 알림도 갈라진다. 일이 꽤 는다 |
| **취소** | 대기 상태는 본인 취소 가능, 승인 뒤에는 교사만 | 승인 뒤 본인 취소를 열면 "잡아두고 안 쓰고 안 지우는" 문제는 줄지만 무단 취소가 생긴다 |
| **신청 기간** | 오늘 ~ 3주 뒤. 당일 신청도 허용 | 승인이 필요하므로 너무 촉박하면 어차피 못 쓴다 |
| **주말·공휴일** | 평일만 | 주말은 학교 개방 여부가 따로 걸리는 문제다 |

### 제한을 두지 않기로 한 것

선생님 입장에서는 "몇 시부터 몇 시까지 방 쓸게요" 에 가깝다. 크게 조일 이유가 없다.

- 한 번에 이어 잡는 교시 수 — **제한 없음**
- 같은 사람이 같은 날 몇 건 — **제한 없음**
- 8·9교시(방과후) 노출 — **그냥 보여준다**
